# Panic screen with a dynamic QR report

The kernel panic screen now carries a **dynamically generated QR code** holding the panic report,
rendered in the top-left with the key data under it, a smaller logo, and the title/reason
left-aligned along the bottom. The full report also goes out over the UART, and the panicking CPU
halts waiting for a machine reset instead of spinning silently.

## What landed

| Piece | File | Notes |
|---|---|---|
| QR Model-2 encoder | `kernel/qr.{h,cc}` | Byte mode, ECC L/M/Q/H, versions 1–40. Reed-Solomon over GF(256) (generator built at runtime), block interleaving, function patterns, alignment, format/version info, all 8 masks with ISO penalty selection. Allocation-free; static working buffers (never the faulting stack). |
| QR spec data | `kernel/assets/qr_tables.json` → `qr_tables.h` | EC block structure, alignment centres, format/version words as **data**, generated by `scripts/gen-qr-tables.py`. `scripts/qr/extract-qr-spec.py` documents provenance. |
| Panic report record | `kernel/panic_report.{h,cc}` | One fixed-capacity record: trap, ESR/FAR/ELR/SPSR/SP, x0–x30, bounded backtrace, hardware/PCI facts, capability denials, build id. Two renderers from the same data: compact for the QR, full for serial. |
| Screen layout | `kernel/panic_screen.cc` | QR top-left (`module = box/(modules+quiet)`, box = min(w/2, 3h/5)), report lines under it, logo scaled into the remaining space, title + reason bottom-left. |
| Panic path | `kernel/panic.cc` | Captures the report, dumps it to the UART via `log::panic_dump`, paints the screen, then halts this CPU (`wfi`) awaiting reset. A first-writer flag parks any second CPU so it cannot clobber the report. |
| Direct UART dump | `kernel/log/log.cc` | `panic_dump()` writes the report raw, bypassing rings/prefixes — a panic must reach the wire even when io.console is not draining yet. |
| Capability denials | `kernel/cap/cap_table.cc` | `cap::denial_count()` counts rejected capability lookups (invalid/revoked handle, type mismatch) for the report. |
| Build fix | `userland/CMakeLists.txt` | Content-hash stamp for the staged Linux artifacts (see below). |

The QR carries the identifying subset: build id, core, reason, ESR/FAR/ELR/SPSR/SP/FP/LR, x0-x7, an
8-frame trace, the hardware/PCI summary, the capability-denial count. The serial dump carries all of
that **plus the complete x0-x30 register file and the full 16-frame trace** — a code large enough to
hold every register at a scannable module size would dominate the screen, which the layout avoids.

Layout is 1:1 on purpose: the logo is drawn on a grid whose pixel footprint is exactly square
(`art_grid()`; an 8x16 glyph cell means two columns equal one row), and the QR panel is square by
construction. On the 1024x768 ramfb the QR is version 20 (97 modules) in a 291x291 px panel — down
from version 31 / 411 px before the payload was compacted — leaving the logo a 688x688 square.

## Verification

- **Spec tables cross-checked.** `kernel/assets/qr_tables.json` was compared against an independently
  produced, multi-source verification of ISO/IEC 18004 (python-qrcode, nayuki/QR-Code-generator,
  zxing): EC block structure 160/160, format information 32/32, version information 34/34, alignment
  centres 39/39, Reed-Solomon generator polynomials 29/29 degrees, total codewords 40/40 — all exact.
- **Encoder ⟷ decoder round trip.** `tests/test_qr.py` runs the encoder over several payloads
  (3 B … 900 B) at L/M/Q/H and decodes each symbol with an *independent* decoder written from the
  spec (`tests/qr_decode.py`): payload, EC level and version must round-trip and every RS block must
  re-check. The decoder is itself validated against `segno`'s output, and the smallest fitting version
  is asserted. Oversized payloads are rejected rather than silently truncated.
- **On-screen QR really decodes.** `AME_VERIFY_PANIC=1` (`scripts/test/panic-screen.py`) boots a
  dev-only kernel that panics as soon as the framebuffer exists, captures the display with a QEMU
  `screendump`, samples the QR out of the framebuffer and **decodes it**, asserting the report text
  (`KERNEL PANIC`, `reason=`, registers, backtrace) is recoverable from the picture.
- **Layout.** `tests/panic_screen_probe.cc` (host) checks 1024×768, 1280×720, 1920×1080, 640×480 and
  400×300: QR anchored top-left and bounded, key data present, logo present, title in the lower half
  and left-aligned, no writes outside the framebuffer, byte-identical re-render.
- **Gate.** `AME_VERIFY_IOMMU=1 AME_VERIFY_ASSIGN=1 AME_VERIFY_CHANNEL=1 AME_VERIFY_GPU=1
  AME_VERIFY_KMS=1 AME_VERIFY_PANIC=1 scripts/verify.sh` → all rows green.

## Review-driven hardening

An adversarial review of the panic path found real defects, all now fixed and guarded:

- **The frame walk could fault inside the handler** and lose the whole report. The backtrace now only
  follows pointers inside the kernel RAM window (and 8-byte aligned), so a stale or attacker-shaped
  `x29` cannot fault there; the panic path is documented as never dereferencing outside RAM.
- **Ownership was claimed after capture**, so a second panicking CPU could overwrite the record.
  `claim_or_park()` now runs first on every entry point; only the first CPU ever touches the record.
- **The panic path no longer takes locks or touches the log ring** (the Fatal path took a doorbell
  spinlock). The whole report leaves through `log::panic_dump()` on the UART only.
- **Interrupts are masked** on entry, so the parked `wfi` state is stable for both trap and explicit
  panics.
- **The logo no longer paints over the report text**: the key-data column is clipped to the QR column
  and `tests/panic_screen_probe.cc` now fails if a caption pixel reaches into the logo band.
- **No silent QR loss**: the screen tries ECC M then L, returns whether a code was drawn, and the
  serial dump records payload truncation or a missing QR.

## Encoder review outcome

A second adversarial review (independent re-implementation, a real scanner via zxing-cpp, and segno as a
second encoder, with ASan/UBSan sweeps) found **no critical or major defects**: 555 varied plus 92
adversarial payloads all decoded, the function-module map matches segno for versions 2-40, and the whole
codeword pipeline (padding/RS/interleave) matched a from-scratch implementation in 640 cases. Its minor
findings were fixed anyway:

- **Penalty rule 3 now counts the quiet-zone margin** (modules outside the symbol are treated as light)
  and counts horizontal and vertical matches separately, so mask selection matches the ISO/Nayuki
  interpretation rather than merely a working one.
- **`fit_version()` no longer overflows** (`8u * len` → `u64`, plus an explicit maximum payload),
  removing a latent path where an absurd length could report "version 1" and make `encode()` over-read.
- **Spec-table bounds are now a compile-time invariant** (`consteval` check on EC-per-block/block counts),
  and the Reed-Solomon helpers guard their degree, so a table edit that would not fit the fixed buffers
  fails the build instead of corrupting memory.
- **Comment corrected**: the encoder's large buffers are static, but it still uses a small bounded stack
  frame; the header now says so instead of claiming zero stack.
- **The on-screen QR is drawn dark-on-light** (light panel, dark modules) rather than inverted, which is
  what real scanners expect; the host test and capture harness follow the change.
- The capture harness now keeps the QEMU monitor socket in a short temp path when the output directory
  is deep (a unix socket path limit, hit while filing the evidence).

## Fixed along the way

The GPU build staged prebuilt Linux artifacts by inlining `copy_if_different` into the `system.mxb`
custom command, with the copies undeclared and, crucially, freshness decided by **mtime** — so an
artifact directory refreshed with older timestamps (`rsync -a`, restored backup) silently kept the
previous payload in `system.mxb` (this is what made the `dango-channel` row time out once). The bundle
now also depends on a **content-hash stamp** for the artifacts, computed when CMake configures, so any
configure→build cycle (which is what `scripts/verify.sh` and the handoff iteration commands do) always
re-stages and re-packs when artifact *content* changes, regardless of timestamps. Verified by changing
an artifact with an old mtime and confirming ninja re-schedules *"Packing Ame signed system bundle"*.

**Stated limit:** a bare `ninja` with no reconfigure still cannot see a content change that comes with
older mtimes — that is ninja's mtime model, not this project's logic. A follow-up will remove the
staging copies altogether (pointing `mksystem.py` at the artifact directory) and/or drive the stamp
from an always-run step, which removes the staging directory as a class of failure.

## Limits (stated, not hidden)

- Payloads larger than a version-40 symbol at the chosen ECC level are truncated (the renderers set a
  truncation flag, and the panic path reports it on the UART); the report is sized to stay inside ECC M.
- The QR is drawn at the largest integer module size that fits the box; a very dense report on a very
  small panel can leave no whole module size, in which case no QR is drawn and the serial dump says so.
  The serial dump is the authoritative record.
- A panic halts only the panicking core. Other cores keep running, so their log lines can interleave
  with the panic dump on the shared UART, and the framebuffer service could in principle repaint;
  recovery is a machine reset (QEMU `system_reset`/Ctrl-Alt-Del at the emulator, or power). The guest
  has no i8042, so Ctrl-Alt-Del is not observable from inside the guest.
- Explicit `panic()`/`panicf()` have no trap frame, so ESR/FAR are zero and the reason is the message;
  hardware faults (`kernel_sync_fault`) carry the full trap state.
