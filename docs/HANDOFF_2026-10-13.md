## 1) USB transfer ledger — DONE and validated

`drv.usb.xhci` (`userland/drivers/usb/xhci/main.cc`) now runs **every**
transfer through `mochi::usb::TransferEngine` with the new bounded
`ExecTable` (`userland/lib/include/mochi/usb/xhci_exec.h`) routing xHCI
transfer events back into engine completions:

- Control transfers: submit_control → start → encode TRBs (ring capacity
  reserved up front) → record (head/status/data TRB physids) → doorbell →
  wait for the published completion → reclaim. A stall at **any** stage
  (including the setup stage) terminates the transfer (`head_phys` matching).
  Short data stages accumulate and stay live until the status stage.
- Keyboard interrupt stream: submit → single NORMAL TRB → record → doorbell;
  terminal report is retained (buffer pinned) under sink backpressure until
  published, then reclaim + re-arm. Exactly one transfer in flight.
- Orphan sweep reclaims timed-out waits once their completion arrives;
  "uncertain DMA is never recycled" semantics preserved.
- Port status changes: detach cancels the stream (`keyboard detached`
  marker); a later attach event re-enumerates that port (event-driven, no
  polling). Tested live via QEMU monitor (see below).
- Boot scope grants: control endpoint (bus policy) + control buffer +
  keyboard endpoint + report buffer, all direct-mapped non-cacheable slices
  of the DMA arena; engine state lives in a 16 KiB CPU arena (event backlog
  4 KiB + exec 2 KiB + engine).

### The bug that was fixed (for future "why does it loop" incidents)

Symptom: after the first key report, the service "republished" the same
report forever (QEMU appeared to re-deliver; it hadn't). A `-trace
"usb_xhci_*"` run proved QEMU delivered **once** (one `fetch_trb TR_NORMAL`,
two `xfer_retry`, one `xfer_success len 8`) while the guest logged ~1,400
publishes. Root cause: `settle_keyboard()` re-marked `report_pending = true`
on every call while the completion was held, so the publish branch re-fired
each service-loop pass and the reclaim/re-arm path never ran. Fix:
`kExecNotified` one-shot flag per terminal completion. Lesson: any
"settle/claim" helper must be one-shot per completion; the post-publish path
must reach reclaim without re-noticing.

Also fixed en route (feature, not bug): setup-stage stall termination
(`head_phys`), and the earlier GET_IDLE hang was a **bad probe** — QEMU
matches the full request word (`HID_GET_IDLE = 0xa102`); sending request
`0x0A` with direction IN stalls. The probe was removed again.

## 2) IOMMU — DONE (validated earlier in the session)

- SMMUv3 bring-up now **registers its backend with the routing core**
  (`register_backend({segment 0, streams 0..sid_limit-1}, g_backend)`),
  failing closed if registration fails. Without this, `backend_for()` always
  returned null and a fresh build silently denied native DMA.
- Fixed quarantine binding desync: the fault path denied a stream but never
  migrated the core binding table, so a later `domain_attach` returned
  `E_BUSY` forever. New `iommu::note_stream_quarantined()` migrates the
  binding to the quarantine domain; `domain_attach`'s existing recovery path
  then re-attaches. Reachable via repeated faults then reassignment (the vm
  assign selftest hit it).
- Validation at that point: full host suite 160/160; `AME_VERIFY_IOMMU=1
  scripts/verify.sh` all rows green including `iommu-dma` (selftest 22
  checks + vm assign 53 checks).
